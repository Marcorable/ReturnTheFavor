# ReturnTheFavor — 기획 문서 (PRD)

> 받은 마음을 잊지 않고, 갚을 때를 놓치지 않게.

## 1. 배경과 문제

살다 보면 누군가에게 받는 것이 생긴다. 생일선물, 결혼식 축의금, 장례식 조의금, 식사 대접, 이사 때 도와준 일 같은 것들이다.
받을 때는 "나중에 꼭 갚아야지" 하고 생각하지만, 막상 그때가 오면 **잊어버리거나**, 기억하더라도 **얼마를, 무엇을 받았는지** 정확히 떠오르지 않는다.

- 생일선물을 받았는데 그 사람 생일을 놓쳤다
- 상대 결혼식에 가야 하는데 내 결혼식 때 얼마를 받았는지 기억나지 않는다
- 상대에게 경조사가 생겼는데, 그 사람이 내 경조사에 왔었는지조차 헷갈린다

## 2. 목표

| 구분      | 내용                                                            |
| --------- | --------------------------------------------------------------- |
| 핵심 가치 | 받은 것을 **빠르게 기록**하고, 갚을 때가 되면 **제때 알려준다** |
| 대상      | 경조사와 선물을 주고받는 일이 많은 개인 (1차: 본인)             |
| 플랫폼    | iOS·Android (React Native + Expo)                               |
| 저장      | 기기 로컬 SQLite (`expo-sqlite`). MVP에는 서버와 로그인 없음    |

### 하지 않는 것 (MVP 범위 밖)

- 회원가입과 서버 동기화 (Supabase 기반 동기화는 이후 검토)
- 다른 사람과 장부 공유
- 송금이나 선물하기 연동

## 3. 핵심 개념

```
Person (사람)
 ├── 생일 (선택, MVP는 양력 생일 1개)
 └── 거래 기록들 (Favor)
       ├── 방향: 받음(received) / 줌(given)
       ├── 종류: 선물 / 현금(경조사비) / 식사·대접 / 도움 / 기타
       ├── 계기: 생일 / 결혼 / 장례 / 출산·돌 / 승진·개업 / 명절 / 기타
       ├── 내용: 품목, 금액, 메모, 사진(선택)
       ├── 날짜
       └── 갚기 상태: 갚을 예정 / 갚음 / 해당 없음
```

### 갚을 시점의 두 가지 유형

1. **날짜가 정해진 경우** (예: 생일선물을 받음 → 상대 생일에 갚기)
   - 상대의 기념일과 연결해서 기념일 전에 알림을 보낸다
   - 직접 지정한 날짜에 알림을 받는 것도 가능하다
2. **날짜를 미리 알 수 없는 경우** (예: 축의금, 조의금 → 상대에게 경조사가 생겼을 때 갚기)
   - 보답 목록에 계속 표시하고 기본 30일 뒤 한 번 알림을 예약한다
   - 알림을 받은 뒤 다시 알림, 날짜 지정, 보답 완료, 해당 없음 중 하나를 선택한다
   - **"이 사람한테 무슨 일이 생겼다"는 순간에 검색해서 바로 확인**할 수도 있다
   - 예: "김철수" 검색 → "2024.05 내 결혼식 축의금 10만 원 받음 (아직 안 갚음)"

## 4. 기능 명세

### P0 — MVP

| #   | 기능              | 설명                                                                                                   |
| --- | ----------------- | ------------------------------------------------------------------------------------------------------ |
| F1  | 받은·준 기록 추가 | 사람, 방향, 종류, 날짜를 필수로 하고 계기, 금액·품목, 메모를 선택 입력. **10초 안에 입력 가능**해야 함 |
| F2  | 사람 관리         | 이름, 관계, 양력 생일, 메모와 보관·복원. 연락처 가져오기와 음력은 이후 검토                            |
| F3  | 보답 일정 설정    | 받은 기록마다 보답 상태와 시점 선택: 상대 생일 / 특정 날짜 / N일 뒤 / 날짜 미정                        |
| F4  | 로컬 알림         | `expo-notifications`로 한 번의 알림을 예약하고 완료·연기·삭제 시 재예약 또는 취소                      |
| F5  | 보답 목록         | 기한 지남 / 오늘·다가옴 / 날짜 미정으로 나누고 알림 설정 여부와 관계없이 표시                          |
| F6  | 사람별 내역       | 한 사람과 주고받은 내역을 시간순으로 표시. 총액과 가치 비교는 MVP에서 제외                             |
| F7  | 검색              | 이름이나 메모로 바로 찾기 (날짜 미정 유형의 핵심 기능)                                                 |
| F8  | 보답 완료         | 준 기록 작성 화면에 사람과 오늘 날짜를 채우고, 저장 시 받은 기록과 1:1로 연결해 함께 완료 처리         |

### P1 — 이후

- 음력 생일과 여러 기념일 지원
- 홈 화면 위젯 (다가오는 일정)
- 금액 참고 정보: "지난번에 10만 원 받았음"을 갚기 화면에 표시
- 사진 첨부 (받은 선물)
- 데이터 내보내기·가져오기 (CSV), Supabase 백업과 기기 간 동기화
- 통계 (연간 경조사비 주고받은 금액)
- 기기 생체 인증 잠금

## 5. 화면 구성 (초안)

```
Bottom Tabs
├── 보답      : 기한 지남 / 오늘·다가옴 / 날짜 미정 / 빠른 기록 추가
├── 사람      : 사람 목록·검색 → 사람 상세 → 시간순 기록
└── 설정      : 알림 권한, 날짜 미정 기본 재알림 간격, 보관된 사람
```

### 주요 흐름: 받은 기록 추가하기

1. 보답 또는 사람 화면에서 `+` 버튼을 누른다
2. 사람을 선택한다 (최근 사람 / 검색 / 새로 추가)
3. 종류와 계기를 고른다 (칩 버튼으로 탭 한 번)
4. 금액 또는 품목을 입력한다
5. 보답 상태와 시점을 고른다: `상대 생일` / `날짜 지정` / `N일 뒤` / `날짜 미정`
6. 저장하면 알림이 자동으로 예약된다

## 6. 기술 설계

| 항목       | 선택                                              | 비고                                             |
| ---------- | ------------------------------------------------- | ------------------------------------------------ |
| 앱         | React Native + Expo + TypeScript                  | 하나의 코드베이스로 iOS·Android 지원             |
| 내비게이션 | Expo Router                                       | 파일 기반 라우팅과 딥 링크 사용                  |
| 저장       | `expo-sqlite`                                     | SQLite를 MVP의 로컬 원본으로 사용                |
| DB 접근    | 저장소(Repository) 경계 + 명시적 SQL 마이그레이션 | Drizzle ORM은 스키마 확정 후 도입 여부 결정      |
| 알림       | `expo-notifications`                              | 플랫폼별 권한과 예약 차이를 어댑터 내부에서 처리 |
| 아키텍처   | 기능별 폴더 + 도메인·저장소·플랫폼 어댑터 분리    | 과한 추상화는 지양                               |
| 서버 확장  | Supabase (Postgres/Auth) 후보                     | MVP 이후 SQLite와의 동기화 정책을 별도 설계      |

### 데이터 모델 (초안)

```ts
type Person = {
  id: string; // client-generated UUID
  name: string;
  relation?: Relation;
  birthday?: { month: number; day: number; calendar: 'solar' };
  memo?: string;
  archivedAt?: string;
  createdAt: string;
  updatedAt: string;
};

type Favor = {
  id: string; // client-generated UUID
  personId: string;
  direction: 'received' | 'given';
  category: FavorCategory;
  occasion?: Occasion;
  amount?: number;
  item?: string;
  occurredOn: string; // YYYY-MM-DD
  memo?: string;
  returnStatus?: 'pending' | 'returned' | 'notApplicable';
  returnPlan?: ReturnPlan;
  returnedByFavorId?: string; // MVP는 받은 기록과 준 기록의 1:1 연결
  nextReminderAt?: string;
  notificationId?: string;
  createdAt: string;
  updatedAt: string;
};
```

실제 SQLite 테이블, 외래 키, 삭제 규칙과 트랜잭션은 MAR-7에서 확정한다.

### 알림 설계 시 주의점

- SQLite에 저장된 보답 상태와 `nextReminderAt`을 원본으로 사용한다.
- OS에 예약한 알림 식별자를 저장하고, 완료·연기·삭제 시 예약을 취소하거나 교체한다.
- 앱 시작과 포그라운드 복귀 시 저장 데이터와 예약된 알림을 재조정한다.
- iOS와 Android의 권한 및 정확한 알림 전달 차이는 플랫폼 어댑터에서 처리한다.
- 음력 기념일은 MVP 이후 기능으로 분리한다.
- 알림 문구 예시: "🎁 3일 뒤 김철수님 생일이에요. 작년에 블루투스 스피커를 받았어요."

### 향후 Supabase 확장 원칙

- MVP에서는 SQLite가 유일한 데이터 원본이며 오프라인에서 모든 핵심 기능이 동작한다.
- 주요 행의 ID는 클라이언트에서 생성한 UUID를 사용해 향후 Postgres와 충돌 없이 대응한다.
- `createdAt`·`updatedAt`을 처음부터 유지하고, 삭제 동기화와 충돌 해결 필드는 서버 도입 시 마이그레이션으로 추가한다.
- 화면과 도메인은 SQLite API를 직접 호출하지 않고 저장소 인터페이스를 사용한다.
- Supabase 도입 시에도 SQLite를 오프라인 저장소로 유지할 수 있지만, 동기화 큐·재시도·충돌 해결·사용자별 접근 제어는 별도 이슈에서 설계한다.

## 7. 개발 단계 (Linear 프로젝트 마일스톤)

1. **M0 제품 정의**: 문제·MVP 범위, 사용자 흐름, 논리 데이터 모델과 저장 규칙 확정
2. **M1 기반 구축**: Expo TypeScript 프로젝트, Expo Router, SQLite·알림 패키지, 테스트·린트·포맷 설정
3. **M2 핵심 기록**: SQLite 스키마와 마이그레이션, 저장소, 사람·기록 CRUD, 타임라인과 검색 (F1, F2, F6, F7)
4. **M3 알림·보답**: 보답 일정, 로컬 알림 어댑터, 보답 목록, 보답 완료와 준 기록 연결 (F3, F4, F5, F8)
5. **M4 MVP 출시**: iOS·Android 권한과 UI 차이, 접근성, 오류 상태, 배포 준비

음력, 위젯, 내보내기, Supabase 인증·동기화 등 P1 항목은 MVP 출시 이후 별도 마일스톤으로 구성한다.
